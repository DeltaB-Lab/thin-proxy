# Cloudflare 部署

## 一键部署到自己的账号

README 的 [Deploy to Cloudflare 按钮](https://deploy.workers.cloudflare.com/?url=https://github.com/DeltaB-Lab/thin-proxy) 使用 Cloudflare 官方模板流程，要求源仓库为 public。

1. 登录自己的 Cloudflare 和 GitHub 账号，选择创建的仓库、Worker 名称及 D1 数据库。
2. 设置两个 Worker Secret，使用独立随机值并保存备份：

   ```sh
   # ADMIN_KEY：管理页面密码，至少 32 个随机字符
   openssl rand -hex 32
   # UPSTREAM_KEY_ENCRYPTION_KEY：恰好 32 随机字节的 Base64
   openssl rand -base64 32
   ```

3. 保留构建命令 `npm run build`、部署命令 `npm run deploy`。部署命令使用绑定名 `DB` 执行迁移，然后发布 Worker。
4. 打开部署结果中的 workers.dev 地址，加上 `/_relay/`，用自己设置的 `ADMIN_KEY` 登录。

公开的 `wrangler.jsonc` 不包含生产账号或自定义域名。D1 ID 是占位值，按钮流程会创建新数据库并更新配置；无须手工填写资源 ID。`.env.example` 只声明两个运行时 Secret，注释中的 `DEPLOY_*` 不属于按钮必填项。后续部署必须保留原加密密钥，不要每次重新生成。

Cloudflare 会在使用者账号内创建仓库和资源；它不会连接原作者的数据库。平台流程说明见[官方部署按钮文档](https://developers.cloudflare.com/workers/platform/deploy-buttons/)。

## 本地开发

需要 Node.js 22.12+：

```sh
npm ci
npm run init:local
npm run db:local
npm run dev
```

打开 `http://localhost:8787/_relay/`，使用 `.env` 中的 `ADMIN_KEY` 登录。`init:local` 仅在文件不存在时生成两个密钥，已有文件不会覆盖。`.env`、本地 D1 状态 `.wrangler/` 和生成的生产配置均已被 Git 忽略。

## 手动创建一个新部署

```sh
npm ci
npm run init:local
npx wrangler login
npx wrangler d1 create thin-proxy
```

把刚创建的 D1 ID 写入 `wrangler.jsonc` 的 `d1_databases[0].database_id`，保留绑定名 `DB`；使用自己的数据库名称和 Worker 名称。Wrangler 通过登录选择账号，默认使用 workers.dev。若不希望资源标识进入 Git，可使用下一节的独立生产配置方式。

通过交互命令上传 `.env` 中已有的两个值，不要把密钥直接写在命令行参数中：

```sh
npx wrangler secret put ADMIN_KEY
npx wrangler secret put UPSTREAM_KEY_ENCRYPTION_KEY
npm run deploy
```

`npm run deploy` 构建管理页面、执行 D1 迁移后发布。已执行的迁移不会重复运行；升级前应先评估新增迁移的兼容性。普通部署不会将 `.env` 上传为运行时 Secret。

## 已有生产环境：配置与公开模板分离

已有自定义域名的生产环境使用 `npm run deploy:production`。它从 `.env`（本地）或 Cloudflare 构建变量（CI）读取下面六项，并生成受 Git 忽略的 `.wrangler.production.json`：

| 配置名 | 含义 |
| --- | --- |
| `DEPLOY_WORKER_NAME` | 已有 Worker 名称，必须与线上一致 |
| `DEPLOY_ACCOUNT_ID` | 已有 Cloudflare 账号 ID |
| `DEPLOY_DATABASE_NAME` | 已有 D1 数据库名称 |
| `DEPLOY_DATABASE_ID` | 已有 D1 数据库 ID，不能使用模板占位值 |
| `DEPLOY_CUSTOM_DOMAIN` | 已绑定的自定义域名，仅主机名，不带协议或路径 |
| `DEPLOY_SELF_HOSTS` | 全部代理入口域名，以逗号分隔，包含自定义域名及其他别名 |

可按 `.env.example` 中的注释填写本地 `.env`。不要把实际值填回示例或公共 Wrangler 配置。进程环境变量优先于 `.env`；CI 不读取本地 `.env`，缺项或格式错误会停止发布。

此路径保留指定的 Worker、D1 和自定义域名，关闭 workers.dev 及预览地址，不运行远端迁移，也不上传或轮换 `ADMIN_KEY`、`UPSTREAM_KEY_ENCRYPTION_KEY`。两个 Secret 继续保存在已有 Worker 中。不要对已有生产 Worker 使用普通 `npx wrangler deploy` 或模板的 `npm run deploy`。

```sh
# 本地验证，再使用独立配置发布到已有 Worker
npm run check
npm run deploy:production

# 检查生成配置，不发布
npm run config:production
npx wrangler deploy --config .wrangler.production.json --dry-run

# 仅在明确需要迁移时执行
npm run db:production
```

`npm run db:production` 使用同一个生产配置和 `DB` 绑定；更换电脑时需要安全迁移 `.env`，不会自动复制 D1。备份应同时保留数据库和原始加密密钥，否则无法解密已有上游和转发 Key。

### Cloudflare Workers Builds

已有生产 Worker 的 **Settings → Builds** 配置：

- 生产分支：`main`；预览分支构建关闭。
- 构建命令：`npm run check`。
- 部署命令：`npm run deploy:production`。
- 在 **构建变量和机密** 中设置上述六个 `DEPLOY_*` 值，可保存为机密以隐藏日志中的值。它们不是 Worker 运行时 Secret。
- 构建监视路径包含 `*`。Node.js 版本由 `.node-version` 固定。

先设置并核对构建变量及部署命令，再推送移除了生产配置的提交。仅修改本地 `.env` 不会配置远端 Builds。不要将两个运行时密钥复制为构建变量，也不要切换生产数据库。

## 运行参数与迁移

- `CONFIG_CACHE_TTL_SECONDS` 默认 30，配置变更最多约一个缓存周期传播。
- `UPSTREAM_TIMEOUT_SECONDS` 默认 30，大于 0 且不超过 300。
- `UPSTREAM_COOLDOWN_SECONDS` 默认 1800，范围 1–86400；仅启用故障转移的 Key 使用冷却状态。
- `SELF_HOSTS` 列出代理的全部入口域名，避免别名回源循环。请求自身主机名会自动参与校验；自定义域名和其他别名需加入此列表。

本地、模板远端及已有生产迁移分别使用 `npm run db:local`、`npm run db:remote`、`npm run db:production`。这些入口校验 Wrangler 的迁移查询补丁，显式读取 `id`、`name`、`applied_at`。升级锁定的 Wrangler 版本前须复核 `scripts/patch-wrangler.mjs`，并通过 `npx vitest run tests/migrations.test.ts`。不要绕过入口直接运行未修补的迁移命令。

公开模板和生产配置都启用 Workers Observability 与调用日志；应用不记录密钥或代理业务内容。Cloudflare 平台日志由平台单独管理。

## 发布后验证

1. 确认远端 `main` 指向目标提交：`git ls-remote origin refs/heads/main`。
2. 在 Cloudflare Builds 中核对同一提交的构建成功，并确认生产版本承接 100% 流量。推送成功不等于部署成功。
3. 检查管理页可访问、未登录管理请求及无 Key 代理请求返回 401。
4. 用原管理密钥登录，确认原有上游和转发 Key 仍存在；确认 D1 绑定、自定义域名、workers.dev 和预览开关未发生意外变化。
5. 构建记录迟迟没有出现时检查仓库连接、分支和路径过滤。已有运行中的构建应等待最终结果，避免并行手动发布掩盖故障。
