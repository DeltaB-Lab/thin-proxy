# Cloudflare 部署

## 在自己的账号部署

需要 Node.js 22.12+ 和 Cloudflare 账号。在仓库目录执行：

```sh
npm ci
npm run init:local
npx wrangler login
npx wrangler d1 create thin-proxy
```

修改 `wrangler.jsonc`，使用自己的资源：

- `account_id`：自己的 Cloudflare 账号 ID。
- `d1_databases[0].database_id`：刚创建的数据库 ID；`database_name` 与实际名称一致，保留绑定名 `DB`。
- 域名：使用 workers.dev 时删除 `routes`，将 `workers_dev` 改为 `true`；使用自定义域名时将 `routes` 改为自己账号下的域名。
- `vars.SELF_HOSTS`：本服务全部入口域名，逗号分隔，防止别名回源循环。不要把代理自身配置为上游。

`npm run init:local` 会生成两个独立密钥并保存到 Git 忽略的 `.env`，已有文件不会被覆盖。将对应值通过以下交互命令写入 Worker Secret，然后初始化数据库并部署：

```sh
npx wrangler secret put ADMIN_KEY
npx wrangler secret put UPSTREAM_KEY_ENCRYPTION_KEY
npm run db:remote
npm run deploy
```

打开 `https://你的域名/_relay/`，使用 `ADMIN_KEY` 登录并配置上游。

`ADMIN_KEY` 至少 32 个随机字符；`UPSTREAM_KEY_ENCRYPTION_KEY` 是恰好 32 随机字节的 Base64 编码。备份时同时保存 D1 和加密密钥；已有上游数据时不要直接更换加密密钥，否则无法解密。普通部署不会上传 `.env`。

## Deploy to Cloudflare 按钮

README 使用 [Cloudflare 官方部署按钮](https://developers.cloudflare.com/workers/platform/deploy-buttons/)。它要求源仓库公开；本仓库目前为私有，因此按钮暂不能用于部署，也不会自动改变仓库可见性。

如果以后将仓库作为公开部署模板发布，需要先完成以下适配：

1. 将模板中的生产账号、域名和 `SELF_HOSTS` 改为适合新账号的配置，并启用可访问的入口。当前根配置服务于现有生产环境，不能直接作为通用模板使用。
2. 保留 `DB` 绑定。按钮流程支持自动创建 D1 并更新资源 ID，但项目仍需执行数据库迁移。
3. 按部署页面提示配置 `.env.example` 声明的两个 Secret，使用真实随机密钥，不使用示例占位值。
4. 构建命令使用 `npm run build`；新环境部署命令使用 `npm run db:remote && npx wrangler deploy`，先初始化 D1。当前生产自动发布仍保持下面的独立迁移方式。

按钮流程会在使用者账号中创建仓库并通过 Workers Builds 部署。以上是公开模板的准备要求，当前尚未完成跨账号按钮部署验证。

## 运行配置

- `DB`：绑定专用 thin-proxy D1 数据库，真实 ID 写入 wrangler.jsonc。
- `ADMIN_KEY`、`UPSTREAM_KEY_ENCRYPTION_KEY`：Worker 运行时 Secret，不是构建环境变量。不要提交到 Git。
- `CONFIG_CACHE_TTL_SECONDS`：30。
- `UPSTREAM_TIMEOUT_SECONDS`：等待上游响应头默认 30 秒，大于 0 且最多 300。
- `UPSTREAM_COOLDOWN_SECONDS`：默认 1800 秒（30 分钟），可配置为 1–86400 的整数；在 `wrangler.jsonc` 的 `vars` 中修改后随 main 发布。失败请求直接返回，客户端重试时跳过冷却上游；全部不可用返回 503 和 Retry-After。故障状态写入 D1 上游 JSON，其他实例随配置缓存刷新同步。上游卡片可手动清除故障，旧请求不能撤销清除。字段兼容旧配置，无需新增迁移；正常请求不增加数据库查询，故障上报及清除产生少量额外读写。
- 请求体直接流式转发，不缓存或重放，无项目自设的 8 MiB 上限；实际大小受 Cloudflare 和上游限制。
- `SELF_HOSTS`：本服务的域名列表。

初始化迁移在首次发布前单独执行：`npm run db:remote`。自动构建不运行数据库迁移，避免构建令牌承担不必要的 D1 写入权限及普通提交更改生产数据。以后新增迁移时，先评估兼容性并显式执行迁移，再发布依赖新结构的代码。

本地和云端迁移分别使用 `npm run db:local`、`npm run db:remote`。项目锁定 Wrangler 4.151.0，安装依赖时自动修补其迁移历史查询，显式读取 id、name、applied_at，避免 `SELECT *`；两个迁移入口会在运行前再次校验补丁。即使安装时使用了 `--ignore-scripts`，也应使用这两个入口，不要绕过检查直接运行未修补的 Wrangler。版本或目标代码变化时命令会停止，需复核 scripts/patch-wrangler.mjs 并通过 `npx vitest run tests/migrations.test.ts` 后再升级。补丁兼容原有 d1_migrations 记录，不重建数据库、不重放已应用的迁移；Cloudflare 已记录的历史查询仍会显示。

生产运行时从 Cloudflare Secret 读取密钥，本地统一在 `.env` 保存管理和加密密钥；普通部署不会上传 `.env`、本地数据库、账号配置或真实上游配置。首次上线后通过管理页面自行添加上游。

## 自定义域名

生产仅通过 `relay.example.com` 访问，Cloudflare Worker 自定义域绑定管理 DNS 与证书。`wrangler.jsonc` 固定 `workers_dev: false`、`preview_urls: false` 和自定义域路由，避免后续发布恢复默认域名。main 以外的分支不自动部署。

本地仓库只使用 `.env` 保存 ADMIN_KEY 和 UPSTREAM_KEY_ENCRYPTION_KEY，已由 `.gitignore` 排除，Wrangler 本地开发直接读取它。换电脑时复制该文件即可保留密钥，不再使用 `.dev.vars` 或 `.dev.vars.production`。本地 D1 与云端 D1 仍各自独立；如果需要保留本地配置，还需搬迁 `.wrangler` 状态。`relay.example.com` 不能作为本服务的上游地址。

## 平台日志

`wrangler.jsonc` 开启 Workers Observability 与 Workers Logs，`head_sampling_rate` 为 1，`invocation_logs` 和 `persist` 均为 true。main 自动发布后，可在 thin-proxy 的 Observability 页面查询调用日志。日志由 Cloudflare 保存，不写入 D1；应用不增加密钥或业务内容的日志输出。
